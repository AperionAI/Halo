# Pointing OpenClaw at Halo

A worked example for the OpenClaw Gateway specifically. The generic
[`CLAW_BOX_SETUP.md`](./CLAW_BOX_SETUP.md) says "set `ANTHROPIC_API_KEY` and
`ANTHROPIC_BASE_URL` in Claw's own config/env" -- true, but where OpenClaw
actually reads those from took real digging in the field. This documents it so
you don't have to.

## Where OpenClaw keeps its Anthropic credential

Not in the main config, and not in the OS keychain. It lives in:

```
agents/<id>/agent/auth-profiles.json
```

Two consequences:

- Its CLI, `models auth paste-token`, only accepts `sk-ant-oat01-` **OAuth
  tokens**. It rejects standard `sk-ant-api03-` Console API keys, and it will
  likewise reject Halo's `sf_live_...` virtual key. **Do not try to register
  Halo's virtual key through that CLI** -- it's the wrong door.
- Installing a plain API key into the profile store at all means writing that
  file directly.

## The clean integration: inject via env, leave the profile alone

Usefully, **OpenClaw prefers the environment variable over its own auth-profile
store.** So the integration doesn't touch `auth-profiles.json` at all:

- Set `ANTHROPIC_API_KEY` to Halo's virtual key (`sf_live_claw_...`) and
  `ANTHROPIC_BASE_URL` to Halo's ingress in the gateway's environment.
- The gateway uses those, so all traffic flows through Halo.
- Your real key can stay untouched in the profile store as an inert fallback --
  there's no risk of the runtime rejecting the `sf_live_` prefix the way its CLI
  rejects `sk-ant-api03-`, because the env var short-circuits the profile store.

This is the integration to use. Register the agent in Halo first (see
[`CLAW_BOX_SETUP.md`](./CLAW_BOX_SETUP.md) step 2 for the stdin-safe way, and
[`HEADLESS.md`](./HEADLESS.md) if the box has no GUI session), then wire the two
env vars into the gateway.

## Where to set the env vars, and the upgrade landmine

The gateway's environment comes from a **generated** file:

```
service-env/ai.openclaw.gateway.env
```

headed:

```
# Generated by OpenClaw. Do not edit while the gateway service is installed.
```

That generated file is the integration point -- add the two lines there:

```
ANTHROPIC_API_KEY=sf_live_claw_xxxxxxxxxxxxxxxx
ANTHROPIC_BASE_URL=http://127.0.0.1:8787
```

**The landmine:** because OpenClaw regenerates that file, an OpenClaw upgrade
(or a `gateway` reinstall/reconfigure) can silently drop your two lines, and
the gateway quietly goes back to talking to Anthropic directly -- no budget cap,
no cache, no visibility, and no error to tell you it happened.

Mitigations:

- **After every OpenClaw upgrade**, re-check `service-env/ai.openclaw.gateway.env`
  for the two Halo lines and re-add them if they're gone. Put this on your
  upgrade checklist.
- **Verify after any OpenClaw change**: send one request and run `halo report`
  (or open the dashboard). If the request doesn't show up, the env vars were
  probably regenerated away -- see the "$0 / nothing shows up" troubleshooting
  in [`CLAW_BOX_SETUP.md`](./CLAW_BOX_SETUP.md).

## Restart to pick it up

Restart the gateway after editing the env file so it re-reads it. If you
installed Halo as a service, make sure Halo is up first, then bounce the
gateway.
